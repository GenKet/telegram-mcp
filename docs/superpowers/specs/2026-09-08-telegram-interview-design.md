# Автономный интервьюер для telegram-mcp

Дата: 2026-09-08

## Задача

Владелец аккаунта говорит одной фразой: «поговори с @clientX, выясни, какой сайт ему нужен».
Claude раскладывает цель на пункты, задаёт вопросы в Telegram, дожидается ответов,
дозадаёт недостающее и в конце отдаёт саммари. Пауза между вопросом и ответом —
от секунд до дней, поэтому диалог должен переживать закрытие Claude Code.

## Решения, принятые на брейншторме

| Развилка | Решение |
|---|---|
| Горизонт ожидания | часы-дни: состояние на диске, процесс переживает сессию |
| Кто формулирует вопросы и решает, что дозадать | Claude. Демон только слушает и никогда не пишет клиенту |
| Контроль отправки | первое сообщение — с подтверждением владельца, дозадачи — автономно |
| Чек-лист | Claude генерирует из свободной формулировки цели; шаблоны не делаем |
| Вопрос вне чек-листа (цена, сроки, созвон, негатив) | клиенту тишина, эскалация владельцу |
| Живой прогон | со второго аккаунта владельца, не на реальном клиенте |

## Не входит в объём

- GPT/OpenAI в контуре интервью: вопросы, разбор ответов и саммари делает Claude.
  `OPENAI_API_KEY` для этой фичи не нужен (в проекте он и не настроен).
- Шаблоны брифов. Формат состояния допускает их добавление позже без переделки.
- Мгновенные автоответы клиенту от демона («принял, уточню») — обсуждалось как
  вариант C и отложено.
- Транскрипция голосовых: пока эскалация владельцу с пометкой «voice».

## Компоненты

1. **`interview_store.py`** — чистая логика без сети и Telethon: создание интервью,
   отметка пунктов, сборка дельты, лимиты, детект «все пункты закрыты». Полностью
   покрывается pytest.
2. **`listener.py`** (демон, `poetry run telegram-mcp-listen`) — держит Telethon,
   подписан на `NewMessage` от peer'ов активных интервью, дописывает входящие в
   состояние, ставит `needs_attention`, пишет heartbeat. Решений не принимает,
   клиенту не пишет никогда.
3. **Тулы `telegram_interview_*`** в MCP-сервере — интерфейс для Claude.
4. **Состояние** — один JSON-файл на интервью в `~/.telegram-mcp/interviews/<id>.json`,
   вне репозитория.

## Поток

```
владелец: "поговори с @clientX, выясни какой сайт нужен"
 ├─ Claude генерирует чек-лист + текст первого сообщения, показывает владельцу
 ├─ владелец подтверждает → interview_send → ушло клиенту, status=waiting
 ├─ демон: клиент ответил → дописал в state, needs_attention=true, heartbeat
 ├─ Monitor будит сессию (или тик /loop, или cron — если сессия была закрыта)
 ├─ Claude читает дельту через interview_pending:
 │   ├─ остались открытые пункты → формулирует дозадачу → interview_send
 │   └─ все закрыты → interview_finish: саммари владельцу и в файл
 └─ спорное → interview_escalate: needs_human, клиенту тишина
```

## Состояние

`~/.telegram-mcp/interviews/<id>.json`:

```json
{
  "id": "clientx-site",
  "peer": "clientX",
  "goal": "выяснить какой сайт нужен",
  "status": "draft | waiting | needs_attention | needs_human | done",
  "escalation": null,
  "checklist": [
    {"id": "type", "question": "Что за сайт — лендинг, магазин, портал?",
     "status": "open | answered | skipped", "answer": null, "asked_at": null}
  ],
  "messages": [{"id": 41, "date": "2026-09-08T10:00:00+00:00", "from": "me | peer", "text": "..."}],
  "last_seen_message_id": 41,
  "sent_count": 1,
  "max_messages": 10,
  "quiet_hours": null,
  "summary": null,
  "created_at": "...",
  "updated_at": "..."
}
```

`status` двигает только код; `checklist[].status` меняет только Claude через `interview_mark`.

## Тулы

| Тул | Поведение |
|---|---|
| `telegram_interview_start` | создаёт файл в `draft` с целью и чек-листом от Claude; клиенту не пишет |
| `telegram_interview_send` | отправляет текст клиенту, ставит `asked_at` покрываемым пунктам, `status=waiting`, `sent_count++` |
| `telegram_interview_list` | все интервью: статус, закрыто/всего пунктов, кто писал последним, жив ли демон |
| `telegram_interview_pending` | дельта: новые сообщения клиента после `last_seen_message_id` + текущий чек-лист |
| `telegram_interview_mark` | отметить пункты закрытыми с извлечёнными ответами, сдвинуть `last_seen_message_id` |
| `telegram_interview_escalate` | `needs_human` + причина; клиенту ничего не уходит |
| `telegram_interview_finish` | саммари в файл и владельцу, `status=done`; `send_to: "me"` — копия в Избранное |

`pending` и `mark` намеренно раздельны: сначала Claude видит сырой ответ, потом решает,
что он закрывает. Если склеить, состояние менял бы тот же вызов, который его читает, и
после обрыва сессии было бы неясно, обработан ответ или нет.

## Ограничители

- `max_messages` (по умолчанию 10) — при достижении `needs_human`, а не «ещё вопросик».
- Два сообщения подряд без ответа клиента запрещены **кодом**: если последнее сообщение
  в `messages` от `me`, `interview_send` отказывает.
- Эскалация без ответа клиенту: вопрос не по чек-листу, цена, сроки, договор, просьба
  созвониться, негатив.
- Одно активное интервью на peer.
- Тихие часы (`quiet_hours`, например 23:00–09:00 локально) — по умолчанию выключены,
  включаются на интервью; при попадании в окно отправка откладывается.

## Риски

1. **Демон и MCP-сервер держат Telethon на одном `SESSION_STRING`.** Параллельные
   подключения работают, но долгоживущий слушатель `updates` может получать дубли или
   пропускать апдейты между коннектами. Поэтому `interview_pending` не считает файл
   источником истины: он всегда дочитывает историю чата от `last_seen_message_id`
   обычным `get_messages`. Демон — ускоритель, а не условие корректности; если он лежал
   сутки, дельта соберётся целиком. Проверяется первым же живым прогоном: демон и
   MCP-сервер поднимаются одновременно, входящее сообщение должно попасть в состояние,
   а тулы — продолжать работать.
2. Демон умирает тихо → heartbeat с временем в файле, `interview_list` показывает
   «listener alive Ns ago» либо «dead».
3. Голосовой ответ клиента → пункт не закрывается, эскалация с пометкой «voice».
4. Флуд-лимиты Telegram — риск низкий: за интервью уходит порядка десяти сообщений.

## Тестирование

- **pytest по `interview_store`**: идемпотентность `mark`, лимит `max_messages`,
  блокировка двух сообщений подряд, детект all-closed, сборка дельты по
  `last_seen_message_id`, тихие часы, отказ на второе активное интервью для peer.
- **Живой прогон** со второго аккаунта владельца — `@pythonkiller228` (user id
  `6558694545`, диалог с ним уже существует): старт с подтверждением, ответ «клиента»,
  автономная дозадача, эскалация на вопрос про цену, финальное саммари.
- **Проверка демона**: убить процесс посреди диалога, ответить «клиентом», убедиться,
  что `pending` всё равно собрал дельту из истории.

## Открытые вопросы

Нет. Пробуждение реализуется в порядке: `Monitor` в открытой сессии, `/loop` или
локальный cron как резерв, `interview_pending` дочитывает историю в любом случае.
